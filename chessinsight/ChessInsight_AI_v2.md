## 1. 프로젝트 개요

### 1.1 한 줄 정의

ChessInsight AI는 체스 대국의 엔진 분석 결과를 근거 기반 자연어로
설명하고, 여러 대국에 걸친 반복 실수와 약점을 탐지해 개인화 훈련 방향 및
정기 리포트를 제공하는 대화형 체스 코칭 플랫폼이다.

v2에서는 같은 구조(엔진이 근거를 만들고 LLM이 설명하는 방식)를
**강한 오픈 엔진과 공개 데이터가 있는 다른 게임**으로 넓힐 수 있는지
검토한다. 확장 후보와 판단은 12장에 정리한다.

### 1.2 해결하려는 문제

체스 플레이어는 대국이 끝난 뒤 엔진 분석으로 최선의 수와 평가치 변화를
확인할 수 있다. 하지만 엔진의 수치와 변형만으로는 다음 질문에 답하기
어렵다.

-   이 수가 왜 좋은 수인가?
-   내가 선택한 수는 어떤 위협이나 기회를 놓쳤는가?
-   비슷한 실수가 여러 대국에서 반복되고 있는가?
-   최근 한 달 동안 실제로 개선된 영역과 여전히 취약한 영역은 무엇인가?
-   다음에는 어떤 유형의 포지션을 집중적으로 훈련해야 하는가?

기존 분석 도구가 대국별 리뷰와 통계 제공에 강점을 가진다면, 이
프로젝트는 대국별 분석을 장기적인 학습 과정으로 연결하고 사용자가
자연어로 후속 질문을 이어갈 수 있도록 설계한다.

### 1.3 목표 사용자

**초기 타깃** - 체스 초보자부터 중급자까지, 레이팅 향상을 목표로 하는
플레이어 - 엔진 분석 결과를 이해하기 어렵거나 반복 실수의 원인을
파악하고 싶은 플레이어 - 자신의 대국 이력을 체계적으로 복기하고 싶은
플레이어

**확장 타깃** - 학생들의 대국을 검토하는 체스 코치 - 여러 학습자의 취약
영역과 개선 추이를 관리하려는 교육 기관 및 클럽

### 1.4 핵심 가치 제안

1.  **설명 가능한 대국 리뷰:** 엔진이 제시한 최선의 수와 실제 수의
    차이를 구체적인 포지션 근거와 함께 설명한다.
2.  **대국 간 패턴 탐지:** 한 판의 실수에 그치지 않고 여러 대국에서
    반복되는 취약점을 찾아낸다.
3.  **대화형 분석:** 사용자가 "왜 이 수가 나쁜가?", "다른 후보 수는
    어땠나?"와 같은 후속 질문을 할 수 있다.
4.  **개선 추적:** 기간별 분석 결과를 비교해 취약점이 줄었는지, 표본이
    충분한지 확인한다.
5.  **자동 리포팅:** 주간·월간 요약과 다음 훈련 권장 사항을 자동으로
    생성한다.

## 2. 주요 기능

### 2.1 PGN 가져오기 및 대국 관리

-   PGN 파일 업로드를 통한 대국 가져오기
-   지원 API를 통한 사용자 대국 이력 연동
-   플레이어 색상, 결과, 날짜, 오프닝, 레이팅 등 메타데이터 정리
-   대국별 분석 상태 및 진행률 표시
-   중복 대국 및 파싱 오류 처리

초기 버전에서는 외부 플랫폼 연동에 앞서 PGN 업로드를 기본 입력 경로로
제공한다. API 연동은 각 플랫폼의 정책과 호출 제한을 확인한 뒤 추가한다.

### 2.2 엔진 기반 대국 분석

-   Stockfish를 활용한 포지션 평가
-   실제 착수와 엔진 추천 수 비교
-   블런더, 미스테이크, 부정확한 수 등 실수 후보 탐지
-   핵심 국면 및 평가치 변화 표시
-   후보 수와 주요 변형 제공
-   사용자가 특정 수를 선택했을 때의 결과와 대안 비교

실수 분류 기준은 엔진 설정, 분석 깊이, 포지션 특성에 따라 달라질 수
있으므로 기준을 명시하고 일관되게 적용한다.

### 2.3 근거 기반 자연어 해설

각 설명은 엔진 평가와 변형을 기반으로 생성한다.

예시 질문: - "이 수가 왜 실수인가?" - "엔진이 추천한 수를 두면 어떤
위협을 막을 수 있었나?" - "상대가 다음에 노린 것은 무엇인가?" - "추천
수와 내가 둔 수의 차이를 비교해줘."

설명에는 가능한 경우 다음 정보를 포함한다. - 해당 포지션의 핵심 전술
또는 전략적 요소 - 실제 수와 추천 수의 차이 - 주요 후속 변형 - 평가치
변화 - 설명의 근거가 된 포지션과 수순

LLM이 체스 판단을 독자적으로 만들어내도록 하지 않는다. 엔진과 분석
계층이 근거를 산출하고, LLM은 그 근거를 이해하기 쉬운 문장으로 변환한다.

### 2.4 여러 대국의 반복 약점 분석

-   반복되는 전술 실수 유형 탐지
-   오프닝별 성과와 취약 구간 분석
-   중반전·종반전에서의 실수 패턴 분석
-   시간 부족과 실수의 동반 발생 여부 탐색
-   특정 유형의 포지션에서 반복되는 판단 오류 요약
-   표본 수가 적은 패턴에 대한 신뢰도 표시

예시 질문: - "최근 30판에서 가장 자주 반복된 실수는 무엇인가?" -
"종반전에서 패배로 이어지는 패턴이 있는가?" - "백과 흑 중 어느 쪽에서
실수가 더 자주 발생하는가?" - "최근 한 달간 개선된 영역과 악화된 영역을
비교해줘."

이 기능은 단순히 통계를 나열하는 데 그치지 않고, 각 발견을 관련 대국과
수순으로 연결해 사용자가 직접 검토할 수 있게 한다.

### 2.5 기간별 실력 분석 및 자동 리포트

-   주간·월간 성과 요약
-   레이팅 및 승률 추이
-   실수 유형별 빈도 변화
-   오프닝·중반전·종반전별 지표 비교
-   이전 리포트와의 변화 비교
-   개인화 훈련 권장 사항 생성

레이팅 변화만으로 실력 향상을 단정하지 않는다. 상대 수준, 대국 수,
시간제어, 표본 크기 등의 맥락을 함께 표시한다.

### 2.6 개인화 훈련 추천

분석 결과를 바탕으로 훈련 우선순위를 제안한다.

예시: - 반복적으로 놓치는 전술 유형의 퍼즐 훈련 - 특정 오프닝에서 자주
발생하는 포지션 복습 - 종반전 실수가 많은 경우 관련 종반전 학습 추천 -
시간 부족과 실수가 함께 나타나는 경우 시간 관리 훈련 제안

추천은 관찰된 데이터와 연결해 설명하고, 데이터가 부족하면 단정적인 권고
대신 추가 관찰을 제안한다.

### 2.7 기존 서비스에서 가져오는 기능 (v2)

3.4·12.8의 조사에서 효과가 확인되었거나 설계가 공개된 기능을 다음과 같이
반영한다.

| 기능 | 출처 | 반영 위치 | 내용 |
|---|---|---|---|
| 레이팅별 "찾기 어려움" | Take Take Take + Maia [G30][G31] | 2.2·2.4 | 수의 손실(Stockfish)과 그 레이팅의 사람이 그 수를 찾을 확률(Maia, MIT)을 함께 계산. **그 수준에서 찾을 수 있었던 수를 놓친 경우만 반복 약점으로 집계**해 "모든 수가 실수"인 초보자 리포트를 막음 |

품질 요건**으로 다룬다. 차별점은 3.5에 정리한다.

### 3.2 경쟁 분석 결론

다음 기능은 이미 경쟁 서비스에서 일부 또는 상당 부분 제공되고 있으므로
단독 차별점으로 내세우지 않는다.

-   엔진 추천 수를 자연어로 설명하는 기능
-   대국별 실수 분석
-   기간별 성과 통계
-   개인화 훈련 제안

차별화는 기능 하나보다 **분석 결과를 장기적인 학습 대화로 연결하는 전체
워크플로**에 둔다.

### 3.3 제안하는 차별화 포지션

1.  **대국 간 패턴을 근거와 함께 설명:** "전술이 약하다"는 요약에서
    끝나지 않고, 반복 패턴이 나타난 대국·수순·포지션을 제시한다.
2.  **자연어 후속 탐색:** 사용자가 분석 결과를 바탕으로 추가 질문을
    이어가고, 특정 주장에 대한 근거를 확인할 수 있다.
3.  **리포트 간 변화 추적:** 지난달에 발견한 약점이 이번 달에 줄었는지,
    데이터가 충분한지 비교한다.
4.  **한국어 학습 경험 최적화:** 체스 용어를 무조건 번역하는 데 그치지
    않고, 초보자와 중급자에게 맞는 설명 수준을 제공한다.
5.  **근거 검증 가능한 설명:** 모든 주요 설명을 엔진 변형, 평가치, 실제
    기보와 연결한다.

이 차별화 가설은 사용자 테스트로 검증해야 한다. 특히 한국어 설명의
품질과 반복 약점 분석이 기존 서비스 대비 얼마나 유용한지 확인해야 한다.

### 3.5 재정의한 차별점 (v2)

조사한 범위에서 아래 조합을 모두 가진 서비스는 확인하지 못했다.

1.  **약점마다 근거 대국·수순을 바로 연결:** 경쟁사 Insights는 통계·요약
    수준이다. "이 약점이 나온 대국과 해당 수"를 클릭 한 번으로 열어 보게
    한다 (3.3 ①을 좁힘).
2.  **리포트 간 변화를 표본 신뢰도와 함께 판정:** 지난달 약점이 줄었는지,
    표본이 충분한지를 함께 보여 주는 서비스는 확인되지 않았다 (3.3 ③ 유지).
3.  **서버 측 출력 검증 후 재생성:** 공개 사례는 화면 표시 단계에서만
    거르거나(loocookie) 오프라인 평가만 한다(Take Take Take). 응답마다 수의
    합법성·증거 포함 여부·숫자 혼입을 검사하고 실패하면 다시 생성한다(4.6).
4.  **레이팅을 반영한 약점 정의:** Maia로 "그 수준이면 찾아야 했던 수"만
    반복 약점으로 집계한다. Take Take Take는 Maia를 수 설명에만 쓰고 대국 간
    집계에 썼다는 언급이 없다 (2.7).
5.  **같은 구조로 다른 게임 확장:** 조사한 체스 서비스는 모두 체스
    전용이다(12장).

한국어 설명은 차별점이 아니라 **국내 시장의 기본 요건**으로 낮춘다.

### 4.2 분석 작업 흐름

1.  사용자가 PGN 파일을 업로드하거나 지원 플랫폼에서 대국을 가져온다.
2.  Spring Boot API가 입력을 검증하고 대국 메타데이터를 저장한다.
3.  분석 요청을 작업 큐에 등록한다.
4.  Python 분석 워커가 PGN을 파싱하고 Stockfish로 주요 포지션을
    분석한다.
5.  분석 계층이 실제 수와 추천 수의 차이, 평가치 변화, 관련 변형을
    구조화한다.
6.  LLM 계층이 구조화된 근거를 바탕으로 자연어 해설을 생성한다.
7.  결과를 데이터베이스에 저장하고 프론트엔드에서 분석 상태와 결과를
    제공한다.
8.  여러 대국의 분석 결과가 누적되면 집계 모듈이 반복 패턴과 기간별
    변화를 계산한다.
9.  리포트 생성기가 분석 결과를 요약하고, 사용자는 리포트에 대해 대화형
    질문을 할 수 있다.

### 4.3 비동기 처리 설계

Stockfish 분석은 대국 길이와 분석 깊이에 따라 시간이 오래 걸릴 수 있다.
따라서 HTTP 요청에서 모든 분석을 동기적으로 끝내기보다 작업 큐를
이용하는 편이 적절하다.

-   API 서버: 분석 요청을 검증하고 작업을 등록한다.
-   RabbitMQ: 대기 중인 분석 작업을 전달한다.
-   분석 워커: 작업을 가져와 엔진 분석을 실행한다.
-   데이터베이스: 작업 상태와 결과를 기록한다.
-   프론트엔드: 작업 상태를 주기적으로 조회하거나 SSE 등으로 진행 상황을
    수신한다.

초기 버전은 모듈을 논리적으로 분리하되, 운영 복잡도를 줄이기 위해 반드시
모든 구성 요소를 독립 마이크로서비스로 배포할 필요는 없다.

### 4.4 LLM 근거 연결 설계

LLM에 "이 포지션을 분석해줘"라고만 요청하면 잘못된 수순이나 근거가
부족한 설명이 생성될 수 있다. 이를 줄이기 위해 분석 계층에서 다음과 같은
구조화된 데이터를 전달한다.

-   현재 포지션의 FEN
-   실제 착수와 엔진 추천 수
-   엔진 평가치와 평가치 차이
-   주요 후속 변형
-   관련 전술·전략 특성
-   설명에 사용 가능한 근거와 제한 사항

LLM은 이 데이터를 바탕으로 설명을 생성하며, 언급한 수순이 실제 엔진
변형과 일치하는지 검증하는 단계를 둔다. 근거가 부족한 경우 원인을
단정하지 않고 불확실성을 표시한다.

### 4.5 게임 어댑터 계층 (v2)

다른 게임을 추가할 때 분석 계층·LLM 계층·리포트를 다시 만들지 않도록,
게임마다 달라지는 부분만 어댑터로 분리한다. MVP는 체스 어댑터 하나만
구현하되 인터페이스는 처음부터 이 형태로 둔다.

| 어댑터 구성 | 역할 | 체스 | 바둑 | 장기·샹치 | 쇼기 |
|---|---|---|---|---|---|
| 기록 파서 | 기보·리플레이를 수순으로 변환 | PGN (python-chess) | SGF | GIB 등 장기 기보 형식, 샹치 PGN 변형 (pyffish 규칙 검증) | KIF·CSA·USI |
| 규칙 엔진 | 합법 수 검증, 포지션 표기 | python-chess (FEN) | 바둑 규칙(한국·중국·일본 룰, 덤) | Fairy-Stockfish 규칙(pyffish) | Fairy-Stockfish 또는 YaneuraOu |
| 엔진 프로토콜 | 평가·후보 수·변형 요청 | UCI (Stockfish) | GTP 또는 KataGo JSON 분석 엔진 | UCI/UCCI (Fairy-Stockfish, Pikafish) | USI (YaneuraOu) |
| 평가 정규화 | 엔진 출력 → 공통 단위 | 센티폰 → 승률 | 승률 + 집 차이(scoreLead) | 센티폰 → 승률 | 평가값 → 승률 |
| 실수 기준표 | 블런더·실수·부정확 기준 | 승률 손실 구간 | 승률·집 손실 구간 | 승률 손실 구간 | 승률 손실 구간 |
| 패턴 태그 사전 | 반복 약점 분류 체계 | 전술 모티프, 국면 단계 | 사활·행마·끝내기 등 | 포 운용·궁성 수비 등 `[정의 필요]` | 위(囲い)·공격 등 `[정의 필요]` |

-   **공통 평가 단위:** 게임마다 엔진 점수 체계가 달라, 실수 판정과 기간
    비교는 "그 수로 잃은 승률(승률 손실)"로 통일한다. 확률 게임
    (백개먼·마작)은 기대값(에퀴티) 손실로 대응한다.
-   **게임별로 다시 만들어야 하는 것:** 패턴 태그 사전, 실수 기준표의
    구간, LLM 설명용 용어집. 이 비용이 확장 비용의 대부분이다.
-   **그대로 재사용하는 것:** 작업 큐, 분석 결과 저장, 기간 비교,
    리포트 생성, 근거 검증(언급한 수순이 엔진 변형과 일치하는지),
    대화형 질의.

### 4.6 LLM 근거 연결 보강 (v2)

4.4를 loocookie/ChessGPT, Take Take Take, CCC, thinkfish의 설계·실패 사례로
구체화한다 [G28][G29][G31][G47].

**① 근거 만들기 (분석 계층)**

| 설계 | 내용 |
|---|---|
| 같은 수 차례끼리 비교 | 최선 라인과 실제 수 라인을 같은 수 차례에서 비교해 첫 수의 차이만 남김. 직전 포지션과 비교하면 "수를 둔 효과"만 측정됨 |
| 변화가 큰 개념 순으로 | 그 수로 가장 크게 변한 특징·개념만 근거로 넘김(CCC, loocookie) |
| 전술은 실제 결과로 확정 | 포크·핀 등은 검출만 하고, 노린 기물이 실제로 잡혀야 근거로 인정 |
| 판 상태 보강 | 수 전후 포지션, 현재 걸려 있는 공격 관계 목록을 함께 전달(thinkfish, CCC) |
| 오프닝 이론 수는 이론이라고만 | 이론 수에 포지션 이유를 지어내지 않음 |

**② LLM에 넘기기 전 정리**

| 원칙 | 내용 |
|---|---|
| 인용하면 안 되는 값은 빼기 | 센티폰·수 차례 번호 등은 단어("근소한 우세", "큰 차이")로 바꾸거나 제거. 프롬프트로 금지하는 것보다 데이터에서 빼는 것이 확실함 |
| 닫힌 질문 유형 | 최선 수 / 형세 / 내 수의 문제 / 대신 둘 수 / 수순 검증 / 반복 약점 / 기간 비교. LLM은 질문 분류만 하고, 유형마다 다른 증거를 보냄 |
| 질문에 없는 정보는 보내지 않기 | "내 수가 왜 별로야?"에는 엔진 최선 수를 보내지 않음(남겨 두면 규칙이 있어도 "대신 X"로 끝남) |
| 필드 이름에 역할 표시 | 배경으로만 쓸 정보는 `background_` 접두어 등으로 구분 |

**③ 설명 거부 기준** (v1 "불확실성 표시"의 구체화)

-   평가치 차이가 일정 값 미만이면 "두 수는 사실상 같음"으로 답하고 이유를
    만들지 않는다 (loocookie는 25cp, 본 서비스는 승률 손실 기준으로
    `[측정 예정]`).
-   근거가 평가 차이의 절반 미만만 설명하면 원인을 말하지 않고 "엔진 판단의
    대부분이 설명되지 않음"으로 답한다.
-   반복 약점·기간 비교는 표본이 기준 미만이면 결론을 보류한다(v1 2.4·2.5).

**④ 서버 측 출력 검증 (차별점, 3.5 ③)**

| 검사 | 실패 시 |
|---|---|
| 언급한 수가 해당 포지션에서 합법인가 | 재생성(최대 N회) 후에도 실패하면 템플릿 설명으로 대체 |
| 언급한 수가 증거(엔진 변형·후보 수)에 있는가 | 같음 |
| 숫자·평가치가 섞였는가 | 같음 |
| 증거에 없는 오프닝·변형 이름을 썼는가 | 같음 |

모든 수는 번호를 붙인 표기(`$7...Qd5` 형식)로 쓰게 해 어느 포지션의 수인지
기계적으로 확인할 수 있게 한다.

**⑤ 평가와 개선 루프**

-   실제 사용자 대국에서 뽑은 시나리오 평가셋(전술, 블런더, 동등한 수,
    환각 유도 사례)을 만들고, LLM 심판이 "주어진 사실만 썼는가"를 채점한다.
    v1 10.1의 근거 일치율로 보고한다.
-   사용자 신고 → 해당 포지션·근거·응답을 묶어 검출기와 프롬프트 개선 과제로
    등록 → 사람 검토 후 반영한다.
-   대국 후 리뷰의 응답 시간 목표를 정하고 모델별 정확도·지연을 비교한다
    (참고: Take Take Take는 3초 이내 목표, 자체 평가셋에서 Gemini Flash 약 75%
    통과).

## 6. 데이터 수집 및 정책 고려 사항

가능한 데이터 입력 경로: - 사용자가 직접 업로드하는 PGN - Chess.com 공개
데이터 API - Lichess API

참고 링크: - Chess.com Published Data API:
https://www.chess.com/news/view/published-data-api - Lichess API:
https://lichess.org/api

구현 전에 각 API의 이용 약관, 인증 요구사항, 호출 제한, 저장·재배포
조건을 확인한다. 사용자 계정 연동은 명시적 동의를 받고, 필요한 범위의
데이터만 수집한다. 플랫폼 API에 의존하지 않도록 PGN 업로드를 대체 경로로
유지한다.

**v2: 체스 공개 데이터 활용**

Lichess는 대국·퍼즐·포지션 평가 데이터를 CC0로 공개하며 연구·상업 이용을
모두 허용한다 [G1]. 사용자 대국과 별개로 다음 용도에 쓴다.

| 데이터 | 규모 (2026-10 확인) | 용도 |
|---|---|---|
| 포지션 평가 (Stockfish) | 약 3.9억 포지션 | 자주 나오는 포지션은 엔진을 다시 돌리지 않고 캐시로 사용해 분석 비용·지연 감소 |
| 대국 (표준·변형) | 월별 PGN, 변형만 해도 앤티체스 약 3,786만 판 등 | 레이팅대별 평균 실수율·오프닝별 기준선 → "같은 레이팅대보다 종반 실수가 많음" 같은 비교 근거 |
| 퍼즐 | 약 606만 개, 레이팅·테마 태그 | 반복 약점 태그와 같은 테마의 퍼즐을 훈련 추천에 연결 |

공개 데이터의 평가 깊이·엔진 버전이 자체 분석과 다를 수 있으므로,
캐시 사용 여부와 엔진 버전을 분석 결과에 함께 기록한다.

## 7. 시장성 및 수익 모델

### 7.1 시장성 가설

기존 서비스가 대국 분석, 자연어 코칭, 장기 통계 및 개인화 훈련 기능을
제공하고 있다는 점은 체스 학습 도구에 대한 실제 제품 생태계와 유료화
모델이 존재함을 보여준다. 다만 경쟁 서비스의 존재만으로 신규 서비스의
수요나 수익성을 입증할 수는 없다.

시장성을 검증하려면 다음을 조사한다. - 초보·중급 플레이어가 현재 분석
도구에서 느끼는 불편 - 한국어 설명에 대한 실제 선호와 지불 의사 - 여러
대국에 걸친 반복 약점 분석의 체감 가치 - 기존 서비스 대비 더 자주
사용하게 되는지 여부 - 코치가 학생별 자동 리포트를 도입할 의향이 있는지
여부

### 7.2 수익 모델 후보

**B2C Freemium** - 무료: 월간 분석 대국 수 또는 고급 리포트 기능 제한 -
유료 구독: 장기 분석, 대화형 질의, 상세 리포트, 개인화 훈련 추천, 분석
이력 비교

**B2B 코치용** - 학생별 대국 관리 - 학생별 반복 약점 및 개선 추이 -
수업용 리포트 내보내기 - 여러 학생의 진행 상황 대시보드

가격은 경쟁 서비스와 사용자 인터뷰, 실험 결과를 바탕으로 결정한다. 초기
기획 단계에서 임의의 시장 규모나 매출 전망을 확정적인 사실처럼 제시하지
않는다.

### 7.3 초기 검증 계획

1.  체스 초보·중급 사용자 10\~15명 인터뷰
2.  사용자가 직접 업로드한 기보로 분석 결과 프로토타입 제공
3.  설명의 이해도, 신뢰도, 유용성 평가
4.  기존 도구로 해결되지 않은 문제와 실제 재사용 의향 조사
5.  무료 사용 이후 유료 기능에 대한 지불 의사 테스트

## 8. MVP 범위

### 포함 기능

-   PGN 파일 업로드 및 파싱
-   Stockfish 기반 대국 분석
-   실수 후보 및 핵심 국면 탐지
-   추천 수와 실제 수 비교
-   근거 기반 자연어 해설
-   대국별 요약 리포트
-   여러 대국에서 반복되는 약점의 기초 통계
-   기간별 비교 리포트
-   리포트 내용에 대한 기본 자연어 질의

### MVP 이후로 미룰 기능

-   실시간 대국 중 코칭
-   자체 체스 엔진 개발
-   복잡한 멀티에이전트 구조
-   초기부터 완전한 마이크로서비스 분리
-   광범위한 소셜 기능 및 랭킹
-   모든 외부 플랫폼의 계정 연동

실시간 대국 중 코칭은 공정성 및 플랫폼 정책 문제를 일으킬 수 있으므로
초기 범위에서 제외한다.

**v2 반영:** MVP의 게임은 체스 하나로 유지한다. 다만 4.5 어댑터
인터페이스와 5장 확장 필드는 MVP에서 함께 구현해, 2단계(바둑) 추가 시
분석 계층을 다시 만들지 않게 한다. 다른 게임은 12.6 로드맵을 따른다.

## 12. 확장 검토: 다른 게임으로의 확장 (v2)

> 2026-10-21 웹 검색 기준. 출처는 14장 [G1]~[G47] 참조. 엔진 강도는 대부분
> 프로젝트 자체 주장이며 독립 검증 수치는 확인하지 못함.

### 12.1 판단 기준

이 서비스의 핵심 구조는 "**엔진이 근거를 만들고, LLM은 그 근거만
설명한다**"이다(2.3·4.4). 따라서 **엔진은 필수**, **공개 데이터는 보조**
기준으로 둔다.

| 기준 | 질문 | 없을 때의 결과 |
|---|---|---|
| **① 최적화된 오픈 엔진 (필수)** | 사람보다 강하고, 수마다 평가·후보 수·변형을 내주며, 상업 서비스에 쓸 수 있는 라이선스의 엔진이 있는가 | "최선 수 대비 손실"을 계산할 수 없어 실수 판정·근거 검증이 불가능. LLM이 판단을 직접 만들게 되어 v1 설계 원칙(2.3)과 충돌. **확장 불가** |
| **② 오픈데이터 (보조)** | 사람 대국 기록을 공개 라이선스로 대량 얻을 수 있는가, 사용자가 기록 파일을 내보낼 수 있는가 | 핵심 기능(대국 분석, 그 사용자의 반복 약점)은 엔진과 사용자 데이터만으로 가능. 다만 아래 기능이 약해지거나 늦어짐 |

**엔진만으로 되는 것과 사람 데이터가 필요한 것**

| 엔진 + 사용자 자신의 대국만으로 가능 | 사람 대국 데이터가 있어야 가능 |
|---|---|
| 수마다 평가·최선 수·변형, 실수 판정 | 같은 레이팅대와 비교("같은 수준보다 종반 실수가 많음") |
| 그 사용자의 대국 간 반복 약점 | 수준별 실수 기준(엔진 기준으로는 초보의 거의 모든 수가 실수) |
| 엔진 학습(자가 대국으로 학습한 엔진은 사람 기보 불필요) | 사람이 둘 법한 대안 제시(Maia 같은 모델은 사람 대국으로 학습) |
| | 약점 태그 체계 검증, 오프닝 통계, 실전 기반 퍼즐 |
| | 평가 캐시를 통한 비용 절감(필수 아님) |

공개 데이터가 없는 게임은 사용자 업로드가 쌓일 때까지 비교 기능이 약하고,
엔진 자가 대국만으로는 사람 기준선을 만들 수 없다. 그러나 기능이 불가능해지지는
않으므로 확장을 막는 조건이 아니라 **출시 범위와 일정을 정하는 조건**으로 본다.

보조 기준: ③ 엔진·데이터 라이선스의 상업 이용 가능성 ④ 한국 수요
⑤ 기록 형식·규칙 엔진이 있어 어댑터(4.5)를 만들 수 있는가 ⑥ 실시간 보조
금지 등 플랫폼 정책.

서드파티로 들어갈 여지가 작다(12.8).

### 12.5 공통 정책: 종료된 기록만 분석

Chess.com은 대국 중 엔진·확장 프로그램·자동 블런더 체크를 금지하고
[G22], Riot도 게임 중 판단을 대신 내려 주는 앱을 금지한다 [G20].
v1 8장의 원칙(실시간 대국 중 코칭 제외)을 모든 게임에 동일하게 적용해,
**종료된 대국 기록·리플레이만 분석**한다. 진행 중인 대국 화면 인식,
메모리 읽기, 오버레이 기능은 만들지 않는다.

**게임 전반의 흐름**

1.  **엔진 복기는 기본 기능이 됨:** 대형 플랫폼이 직접 탑재하는 추세
    (타이젬, 天天象棋, 작혼 MAKA, 체스의 Chess.com). 엔진 리뷰만으로는
    서드파티의 설 자리가 줄어든다.
2.  **LLM 설명은 초기 단계이고 형태가 갈림:** 중계 해설(쇼기), 대화형
    튜터(백개먼), 리플레이 총평(스타크래프트). **개인 대국을 모아 반복 약점을
    근거와 함께 설명하는 형태는 어느 게임에서도 확인하지 못함** → 3.5 차별점이
    다른 게임에서도 유효하다.
3.  **대국 간 추적은 두 갈래:** 보드게임은 실수의 퀴즈·간격 반복, 온라인
    게임은 역량 점수의 추세. 본 서비스는 두 방식을 모두 반영한다(2.7).
4.  **온라인 게임의 한계 지적:** AI 리뷰가 통계만 읽어 흐름이 넘어간 순간과
    그 원인이 된 행동을 놓친다는 평가가 있음 [G45]. 엔진이 없는 게임에서
    설명 품질의 상한을 보여 주는 사례.

## 13. 최종 제안

**프로젝트명:** ChessInsight AI\
**주제:** 대화형 체스 코칭 및 실력 분석·자동 리포팅 플랫폼

이 프로젝트의 핵심은 단순히 엔진의 최선 수를 알려주는 것이 아니다. 엔진
분석을 검증 가능한 근거와 함께 설명하고, 여러 대국에서 반복되는 취약점을
찾아내며, 사용자가 대화형으로 원인을 탐색하고 개선 여부를 추적하도록
만드는 것이다.

기술적으로는 Stockfish 기반 분석, Python 체스 데이터 처리, Spring Boot
API, 비동기 작업 큐, PostgreSQL, LLM 기반 자연어 설명을 결합할 수 있다.
AI와 백엔드 양쪽에서 구현 과제가 분명하며, 엔진 분석과 생성형 AI의
역할을 분리해 결과의 신뢰도를 평가할 수 있다는 장점이 있다.

사업적으로는 기존 경쟁 서비스와의 기능 중복을 인정하고, **근거가 연결된
장기 패턴 분석과 대화형 학습 워크플로**가 실제 사용자에게 더 큰 가치를
주는지 검증하는 것이 중요하다. 따라서 초기 MVP는 PGN 업로드, 엔진 분석,
근거 기반 해설, 반복 약점 요약, 기간별 리포트에 집중하고 사용자 테스트를
통해 확장 우선순위를 결정한다.

**v2 확장 판단:** 이 구조는 **강한 오픈 엔진이 있는 게임**에서만 그대로
옮겨 갈 수 있다. 검토 결과 바둑(KataGo, MIT·상업 이용 가능)이 가장 유리하고,
장기(Fairy-Stockfish)는 엔진은 있으나 공개 데이터가 없어 기준선을 직접
만들어야 한다. 스타크래프트는 데이터는 있으나 평가 엔진이 없어 분석 방식이
달라지므로 별도 제품으로 검토하고, 부루마블·뱅! 같은 현대 보드게임과
LoL은 엔진·데이터가 없거나 경쟁·정책 제약이 커서 확장 대상에서 제외한다.
MVP는 체스로 유지하되 게임 어댑터 구조를 처음부터 적용해 바둑 추가 비용을
낮춘다.

경쟁 조사 결과 "엔진이 판정하고 LLM이 설명하는" 구조와 대국 간 약점 통계,
한국어 설명은 이미 존재한다. 따라서 차별점은 **약점마다 근거 대국·수순 연결,
리포트 간 변화의 표본 신뢰도 판정, 서버 측 출력 검증, 레이팅을 반영한 약점
정의**로 좁히고(3.5), 이 조합이 다른 게임에서도 비어 있다는 점(12.8)을 확장의
근거로 삼는다.
